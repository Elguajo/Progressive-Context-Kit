# Модель памяти проекта

> **Документация только для человека.** Она живёт только во Framework Source и не попадает в Project Runtime.
>
> English: [`PROJECT_MEMORY_MODEL.md`](PROJECT_MEMORY_MODEL.md)

Progressive Context работает устойчиво, когда у каждого долговременного факта есть один канонический владелец.

Схема: [`../visuals/project-memory-model.md`](../visuals/project-memory-model.md)

## Роли документов

### `PROJECT_BRIEF.md`
Отвечает: **Что мы создаём, для кого, с какими ограничениями и как понимаем, что продукт успешен?**

Хранит продуктовую цель и scope, но не историю реализации.

### `ARCHITECTURE.md`
Отвечает: **Как система устроена сейчас?**

Хранит текущий stack, system shape, trust boundaries, важные integrations и operational assumptions.

### `ROADMAP.md`
Отвечает: **В каком порядке мы строим продукт и какая Phase сейчас активна?**

Хранит порядок и статусы phases, но не task-level детали реализации.

### Текущая Phase
Отвечает: **Что мы делаем сейчас, каковы acceptance criteria и как это будет проверено?**

Хранит план и критерии, а также владеет соседним архивом `<phase-name>.prompts.md`: исходные запросы, сохранённые промпты задач с ID, версии, проверку актуальности и наблюдаемые результаты/evidence. При изменении инструкций добавляется новая версия со ссылкой на старую. В обычный контекст попадает только исполняемый текст и краткое состояние активной записи; исходный запрос и история evidence читаются по необходимости.

### `Completion Record`
Отвечает: **Что следующая Phase должна знать без чтения всей предыдущей?**

Это намеренно компактный мост между фазами.

### Phase Completion Report
Отвечает: **Что реально произошло в завершённой Phase в объёме, достаточном для будущего расследования?**

Это durable cold history. Он не должен конкурировать с Brief, Architecture, Roadmap или ADR как текущая истина.

### ADR
Отвечает: **Почему было принято одно consequential решение?**

ADR нужен для rationale, которое должно жить независимо от конкретной Phase.

### `NEXT_SESSION.md`
Отвечает: **Что следующая сессия должна знать и сделать сразу?**

Это volatile hot navigation с `Active task prompt` — ссылкой на запись в фазе. Обновляется при изменении состояния/навигации; исполняемый промпт здесь больше не перезаписывается. Перед работой агент сверяет запись с текущей фазой, кодом, критериями, блокерами и разрешениями, даже если ранее она была отмечена CURRENT.

## Правило ownership

Когда факт меняется, сначала обновляй его канонического владельца.

Примеры:

- изменилась структура системы → обновить `ARCHITECTURE.md`;
- Phase завершена → создать Phase Completion Report и компактный `Completion Record`;
- важному архитектурному решению нужна отдельная причина → создать/обновить ADR;
- изменилось ближайшее действие → перезаписать `NEXT_SESSION.md`.

Не решай неопределённость копированием одного и того же долговременного факта в несколько документов.
